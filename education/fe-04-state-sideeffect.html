Runnable · Frontend Lecture · 04

상태와 부수효과를 가르다
— store vs sideeffect

같은 도메인을 다룬다고 한 곳에 몰아넣으면 안 됩니다. '무엇인지'와 '그걸로 무엇을 하는지'는 서로 다른 책임입니다. 경로정보가 무엇인지를 담는 자리(store)와, 그 상태를 들고 서버·지도와 무엇을 하는지를 담는 자리(sideeffect)를 왜·어떻게 가르는지 — 이 챕터에서 Runnable 의 실제 코드로 짚습니다.

난이도 ★★☆ 선행: 03 MVVM 키워드 store · sideeffect
01 / TWO ROLES

두 개의 역할, 두 개의 자리

하나의 도메인(경로정보)이라도 책임이 다르면 파일을 가릅니다. 왼쪽은 상태, 오른쪽은 그 상태로 바깥세계와 부딪히는 동작.

store — entities/*/model

순수 상태 컨테이너입니다. Nuxt 의 useState 위에 선 반응형 상태와, 그 값을 동기적으로 바꾸는 함수만 가집니다. Cesium 도 네트워크도 모릅니다 — "지금 경로정보가 무엇인지"만 안다. 앱 전역에서 단 하나의 출처(single source of truth) = MVVM 의 ViewModel state.

sideeffect — features/*/api

store 를 들고 바깥세계와 부딪히는 자리입니다. $fetch 로 서버와 통신하고, Cesium 마커를 렌더링하고, 지도 클릭 핸들러를 등록하고, store 를 watch 합니다. 순수한 service 가 아니라 application service + view 어댑터의 합성물 — 그래서 store 와 한 칸에 둘 수 없습니다.

핵심은 방향입니다. store 는 안쪽(상태)만 보고, sideeffect 는 store 를 들고 바깥(서버·지도·이벤트)을 향합니다. 상태가 부수효과를 알면 안 되지만, 부수효과는 상태를 알아야 한다 — 의존은 한 방향으로만 흐릅니다.

02 / MVVM MAP

MVVM 위에 다시 얹어보기

03장의 MVVM 4계층이 Runnable 디렉터리에 어떻게 내려앉는지, 그리고 왜 굳이 가르는지.

MVVM ↔ Runnable

Model = shared/types · schemas · server
ViewModel state = entities/*/model store
부수효과·Presenter = features/*/api sideeffect
View = *.vue

매핑: 계층 → 디렉터리

왜 나누나

테스트: store 는 순수 단위테스트, sideeffect 는 $fetch·Cesium 모킹. 생명주기: store 는 전역, sideeffect 는 viewer 종속 자원. 재사용: UI 는 상태만 구독하면 된다.

이유: 테스트·생명주기·재사용

진짜 service 는 따로

여기서 sideeffect 의 "service"는 클라이언트 측 어댑터입니다. 비즈니스 로직의 진짜 service 는 서버에 있습니다 — server/services/route.service.ts.

위치: 서버 도메인 로직

그래서 sideeffect 를 "service"라 부르되 오해는 금물입니다. 클라이언트 sideeffect 는 상태를 바깥세계에 잇는 다리이고, 도메인 규칙을 책임지는 서버 service 와는 역할이 다릅니다. 둘을 같은 단어로 부른다고 같은 일을 하는 게 아닙니다.

03 / IN RUNNABLE

route-info 한 쌍을 펼쳐보기

경로정보(route-info) 기능은 store 한 파일, sideeffect 한 파일로 정확히 갈라져 있습니다.

// entities/route/model/useRouteInfoStore.ts  — 상태만
const routeInfos        = useState('routeInfo.data', () => [])       // 서버 저장본
const draftRouteInfos   = useState('routeInfo.draftData', () => [])  // 미저장 초안
const isAddingRouteInfo = useState('routeInfo.isAdding', () => false)  // 추가 모드

const toggleAddingMode  = () => { isAddingRouteInfo.value = !isAddingRouteInfo.value }
const addDraftRouteInfo = (item) => { draftRouteInfos.value = [...draftRouteInfos.value, item] }
const clearRouteInfos   = () => { /* 모든 상태 초기화 */ }
// → Cesium·$fetch 단어는 단 한 번도 등장하지 않는다
// features/route-info/api/useRouteInfoSideeffect.ts  — 동작
const store = useRouteInfoStore()                          // 상태를 들고 온다

const fetchRouteInfos     = async (id) => $fetch(`/api/routes/${id}/feedbacks`)
const submitRouteInfo     = async (id, input) => $fetch(...)   // 서버 통신
const saveLocalRouteInfos = async (id) => { /* 초안 일괄 저장 */ }
const renderRouteInfoMarkers = () => { /* Cesium 마커 그리기 */ }

watch(                                                       // 상태가 바뀌면
  [() => store.routeInfos.value, () => store.draftRouteInfos.value],
  () => renderRouteInfoMarkers(),                            // 마커 재렌더
  { deep: true }
)

흐름을 따라가 보면: $fetch 서버 응답 → store.routeInfos 갱신 → watch 감지 → renderRouteInfoMarkers 호출. store 는 자기가 바뀌었다는 사실만 알릴 뿐, 지도를 그릴 줄은 모릅니다. 그 "그리기"는 전부 sideeffect 쪽에 모여 있습니다 — 이게 가른 보람입니다.

04 / MENTAL MODEL

한 문장으로 가르는 기준

한 문장 멘탈 모델

store 는 경로정보가 "무엇인지"를 담당하고, sideeffect 는 그걸로 지도·서버와 "무엇을 하는지"를 담당한다. 새 코드를 어디 둘지 고민될 때는 이 한 문장만 물어보면 된다 — "이건 상태인가, 상태로 하는 일인가?"
