Runnable · Frontend Lecture · 06

데이터는 어떻게 컴포넌트 사이를 흐르나
— 컴포넌트 통신

화면은 수많은 컴포넌트의 트리입니다 — 그리고 그 트리 안에서 데이터는 명시적인 경로를 따라 흘러야 합니다. 이 챕터는 props·emit·slots·provide/inject 가 데이터를 어떻게 전달하는지, 그리고 Runnable 의 FSD 구조에서 통신이 어떤 경계를 따르는지를 다룹니다.

난이도 ★★☆ 선행: 02 컴포저블 키워드 component communication
01 / WHY

컴포넌트는 혼자 살지 않는다

화면은 작은 컴포넌트들의 트리입니다. 데이터가 그 사이를 흘러야 합니다.

컴포넌트는 격리된 섬이 아닙니다. 지도 페이지 하나만 봐도 — 경로 목록·지도 캔버스·고도 차트· 슬라이드오버 패널이 동시에 같은 "선택된 경로 ID"를 알아야 합니다. 이 데이터를 컴포넌트들이 공유하는 방법이 잘못되면 화면이 어긋나거나, 변경 추적이 불가능해집니다.

전역 변수로 막 공유 (나쁜 예)

// 어느 파일에선가…
window.selectedRouteId = 'route-42'

// 다른 컴포넌트에서…
const id = window.selectedRouteId
// 누가 바꿨는지? 언제 바뀌는지?
// 리액티브하지 않음 → 화면 갱신 없음

변경 주체를 알 수 없다. 반응형도 작동하지 않는다. 컴포넌트가 많아질수록 버그 추적이 불가능해진다.

명시적 통신 경로 (올바른 예)

// 부모가 props 로 내려준다
<RouteCard :routeId="selectedId" />

// 자식이 emit 으로 올려 요청한다
emit('select', routeId)

// 변경 주체·경로가 코드에 드러난다

누가 데이터를 소유하고, 어떤 경로로 흐르는지 코드에 선언된다. 반응형과 결합하면 화면도 자동으로 따라온다.

02 / DOWN & UP

props 는 아래로, emit 은 위로

Vue 의 단방향 데이터 흐름 — 자식은 props 를 직접 못 바꾼다. 바꿔달라고 emit 으로 요청한다.

부모 — props 로 내려주기

<!-- ParentPage.vue -->
<template>
  <RouteCard
    :route-id="selectedId"
    :title="route.title"
    @select="onSelect"
  />
</template>

<script setup>
const selectedId = ref<string | null>(null)
const onSelect = (id: string) => {
  selectedId.value = id  // 부모가 상태를 소유·변경
}
</script>

자식 — emit 으로 올려 요청

<!-- RouteCard.vue -->
<script setup>
const props = defineProps<{
  routeId: string
  title: string
}>()

const emit = defineEmits<{
  select: [id: string]
}>()

const handleClick = () => {
  // props.routeId = '…'  ← 직접 변경 금지!
  emit('select', props.routeId)  // 요청만
}
</script>

핵심 규칙: 자식은 props 를 직접 수정할 수 없습니다. 자식이 변경을 원한다면 emit 으로 부모에게 "바꿔달라"고 요청하고, 부모가 상태를 바꾸면 props 가 자연스럽게 새 값으로 내려옵니다. 데이터는 항상 위에서 아래로 흐르고, 변경 요청은 아래에서 위로 올라갑니다.

03 / SLOTS

구조는 비워두고, 내용은 채우게

slot 은 컴포넌트의 "내용 자리 표시자"입니다 — 껍데기(구조·스타일)와 속살(내용)을 분리합니다.

BottomDrawer 나 팝업 모달처럼 열고 닫히는 구조는 공통이지만 내부 내용은 매번 다른 컴포넌트를 만들 때 slot 이 핵심입니다. 껍데기 컴포넌트는 레이아웃·애니메이션·접근성만 책임지고, 실제 내용은 사용처에서 채워 넣습니다.

껍데기 — slot 으로 내용 자리 확보

<!-- BottomDrawer.vue (껍데기) -->
<template>
  <Teleport to="body">
    <div v-if="isOpen" class="drawer">
      <header class="drawer-header">
        <slot name="header">기본 제목</slot>
      </header>
      <main class="drawer-body">
        <slot />  <!-- default slot -->
      </main>
    </div>
  </Teleport>
</template>

사용처 — 내용을 채워 넣기

<!-- RouteInfoPanel.vue (사용처) -->
<BottomDrawer :is-open="isOpen">
  <!-- named slot -->
  <template #header>
    경로 상세 정보
  </template>

  <!-- default slot -->
  <RouteDetailContent
    :route="selectedRoute"
  />
</BottomDrawer>

named slot(#header)을 쓰면 여러 자리를 동시에 채울 수 있습니다. Runnable 의 create-bottom-drawer / create-popup-modal 스킬이 바로 이 패턴 — 구조·모션·오버레이는 껍데기 컴포넌트가, 비즈니스 내용은 slot 이 담당합니다.

04 / PROVIDE-INJECT

깊은 전달 — prop 릴레이를 끊다

트리가 깊어지면 props 를 중간 컴포넌트들이 줄줄이 받아 전달해야 합니다 — 이걸 "prop drilling"이라 부릅니다. provide/inject 가 이를 끊습니다.

prop drilling — 중간 컴포넌트가 피해자

<!-- A → B → C → D 로 전달해야 할 때 -->
<!-- A.vue -->
<B :user="user" />

<!-- B.vue — 쓰지도 않는데 받아서 전달 -->
<C :user="user" />

<!-- C.vue — 마찬가지 -->
<D :user="user" />

<!-- D.vue — 여기서야 실제로 씀 -->

B와 C는 user 를 전혀 쓰지 않는데도 props 로 받아서 아래로 넘겨야 합니다. 컴포넌트가 쓸데없이 결합됩니다.

provide/inject — 필요한 자손이 직접 주입

<!-- A.vue (조상) -->
provide(USER_KEY, user)

<!-- B.vue, C.vue — props 불필요 -->
<!-- (그냥 자식 컴포넌트만 렌더) -->

<!-- D.vue (자손) -->
const user = inject(USER_KEY)
// B·C 를 거치지 않고 바로 받는다

B와 C는 아무 역할 없이 깨끗합니다. D 는 필요한 것만 직접 꺼냅니다.

Runnable 의 useMapPageContext / useOverlayContext 가 정확히 이 역할을 합니다. 지도 페이지(부모 layout)가 facade·flow·auth·네비게이션 핸들을 한 번 생성하고, nested route 로 분리된 탭 패널들(목록·그리기·탐색)이 props 릴레이 없이 inject 로 바로 꺼내 씁니다. 

// widgets/map-page/model/useMapPageContext.ts
export const MAP_PAGE_CONTEXT: InjectionKey<MapPageContext> = Symbol('map-page-context')

// 부모 페이지(pages/index.vue)에서
provide(MAP_PAGE_CONTEXT, {
  facade, flow, slideOver, authStore, selectNav, fetchRoutes
})

// 자식 탭 패널(pages/index/draw.vue 등)에서
const { facade, flow } = useMapPageContext()
// inject(MAP_PAGE_CONTEXT) 로 위 값을 꺼낸다
// 중간 레이어를 전혀 거치지 않는다
05 / IN RUNNABLE

FSD 경계에서의 통신

Runnable 은 Feature-Sliced Design 을 씁니다. 컴포넌트끼리 직접 교차 호출하지 않고, 계층 경계를 따릅니다.

FSD 의 단방향 의존 규칙: pages → widgets → features → entities → shared. 아래 레이어는 위 레이어를 절대 import 하지 않습니다. 그러면 각기 다른 slice 에 속한 컴포넌트들이 어떻게 협력하나? — 그게 widget facade의 역할입니다.

pages

라우트 진입점. widget 을 조합해 레이아웃을 구성하고, MapPageContext 를 provide 한다.

통신: provide → widget

widgets / facade

여러 feature·entity 를 조합해 하나의 동작 단위를 만든다. use*Facade.ts 가 조합점.

통신: inject 받고 emit 으로 올린다

features

단일 사용자 행위(경로 그리기·저장·최적화 등). store 에서 읽고, sideeffect 로 쓴다.

통신: store 경유 — 직접 props 없음

entities / shared

도메인 타입·store·유틸. 어떤 레이어에서도 import 할 수 있다.

통신: store state 만 노출 
// widgets/map-page/model/useRouteDrawingFacade.ts (발췌)
export const useRouteDrawingFacade = (deps: {
  optimizationFacade: ReturnType<typeof useRouteOptimizationFacade>
  terrainFacade:      ReturnType<typeof useRouteTerrainFacade>
  elevationFacade:    ReturnType<typeof useRouteElevationFacade>
}) => {
  const store = useRouteDrawStore()       // entity store 주입
  const notification = useNotificationStore()

  // feature sideeffect 들을 조합해
  const drawEffect = useRouteDrawSideeffect({ ... })

  // 컴포넌트에 공개할 drawing 객체만 반환
  return { drawEffect, drawing, startDrawing, restartDrawing }
}

facade 는 복잡한 조합을 숨기는 담장입니다. 컴포넌트(draw.vue)는 facade 가 반환한 drawing 객체만 알면 됩니다 — entity·feature 의 내부 구조를 몰라도 됩니다. 이게 FSD 에서 통신이 작동하는 방식입니다.

06 / MENTAL MODEL

통신은 곧 계약이다

한 문장 멘탈 모델

통신은 곧 계약이다 — props 로 무엇을 받고 emit 으로 무엇을 알릴지 선언하는 순간, 컴포넌트는 재사용 가능한 부품이 된다. slot 은 구조와 내용의 계약, provide/inject 는 조상과 자손 사이의 계약 — 계약이 명시될수록 어디서든 교체할 수 있고, 어디서든 믿고 쓸 수 있다.

    • c) 전역 상태를 window 에 저장해 어느 컴포넌트든 접근하게 하는 역할
