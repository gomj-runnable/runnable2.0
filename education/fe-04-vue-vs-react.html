같은 웹, 다른 선택
— Vue vs React

Vue 도 React 도 똑같이 브라우저에서 도는 웹 프레임워크입니다. 그런데 한쪽은 흔히 MVVM 이라 불리고, 한쪽은 아닙니다. 둘을 가르는 건 플랫폼이 아니라 단 하나의 선택입니다 — "반응형 양방향 바인딩을 채택했느냐." 이 챕터는 그 갈림길을 따라가며, 왜 같은 웹인데 한쪽만 MVVM 인지를 풉니다.

난이도 ★★☆ 선행: 02 MVVM 키워드 binding
01 / BINDING

MVVM 의 본질은 '반응형 바인딩'

MVVM 을 가르는 핵심은 화면 종류가 아니라, 상태와 화면이 자동으로 묶여(bind) 서로를 따라오느냐 입니다.

MVVM 에서 ViewModel 은 화면이 보여줄 상태를 들고 있고, 바인딩이 그 상태와 View 를 자동으로 동기화합니다. Vue 는 바로 이 바인딩 메커니즘을 언어 차원에서 제공합니다 — ref·reactive·computed·watch 가 곧 ViewModel 이자 바인딩입니다. 그래서 Vue 는 전형적인 MVVM 으로 분류됩니다. 

// Vue — ViewModel 이 곧 반응형 상태, 바인딩은 자동
const count = ref(0)            // ViewModel 의 상태
const doubled = computed(() => count.value * 2)

// 템플릿(View)은 상태에 "묶여" 있다 — 양방향
<input v-model="count" />       // 입력 → 상태 자동 반영
<span>{{ doubled }}</span>          // 상태 → 화면 자동 반영

Vue 창시자 Evan You 도 초기에 MVVM 의 영향을 직접 언급했고, 한동안 반응형 인스턴스를 vm(ViewModel) 이라는 변수명으로 부르던 시절도 있었습니다. Vue 의 뿌리에 MVVM 이 박혀 있다는 증거죠.

02 / REACT IS DIFFERENT

React 는 일부러 바인딩을 버렸다

React 는 양방향 바인딩을 의도적으로 포기하고, 데이터가 한 방향으로만 흐르는 구조를 택했습니다.

Vue — 양방향 reactive

const name = ref('')

// v-model 이 양방향을 자동 연결
<input v-model="name" />
// 입력하면 name.value 가 알아서 바뀐다

상태와 입력이 서로 묶인다. 동기화는 프레임워크가 책임 → MVVM 의 ViewModel 바인딩 그 자체.

React — 단방향 setState

const [name, setName] = useState('')

// props down: 상태 → 화면
<input value={name}
  // events up: 이벤트 → 직접 setState
  onChange={e => setName(e.target.value)} />

상태는 위에서 아래로(props down), 변경 요청은 이벤트로 위로(events up). 동기화를 네가 명시한다.

이게 React 의 단방향 데이터 흐름(Flux 사상)입니다. 양방향 바인딩의 "마법"을 포기한 대가로, 데이터가 어디서 어떻게 바뀌는지를 명시적으로 추적할 수 있게 됩니다. 그래서 React 는 보통 MVVM 이 아니라 단방향 아키텍처로 분류됩니다 — 같은 웹이어도 선택이 다른 것입니다.

03 / SAME FAMILY

MVVM 은 하나의 가문이다

반응형 바인딩을 채택한 프레임워크들은, 플랫폼이 달라도 같은 조상을 공유합니다.

WPF

데스크톱의 원조 MVVM(2005). {Binding} 으로 View ↔ ViewModel 양방향 바인딩.

분류: MVVM (원조)

SwiftUI

iOS 선언형 UI. @State/@Binding 이 곧 반응형 바인딩.

분류: MVVM

Jetpack Compose

안드로이드 선언형 UI. mutableStateOf 가 반응형 상태.

분류: MVVM

Vue

웹 반응형의 대표. ref/v-model 로 양방향 바인딩.

분류: MVVM

React

양방향 바인딩 대신 setState + 단방향 흐름. 같은 가문이 아니다.

분류: 단방향 (MVVM 아님)

오해하기 쉬운 점 — SwiftUI·Compose 가 MVVM 인 건 "모바일이라서"가 아닙니다. Vue·SwiftUI·Compose·WPF 가 모두 반응형 바인딩이라는 MVVM 공통 조상을 공유하기 때문입니다. 플랫폼(웹·iOS·안드로이드·데스크톱)은 제각각이지만, 상태↔화면을 자동으로 묶는다는 설계 철학이 같으면 같은 가문입니다. React 만 그 철학에서 의도적으로 빠져나온 것이죠.

04 / WHY CARE

이름표보다 중요한 질문

"이건 MVVM 이야?" 보다 중요한 건, 상태→화면 동기화를 누가 책임지는가 입니다.

패턴 이름표(MVVM·Flux·MVC)는 결국 같은 질문에 대한 서로 다른 답일 뿐입니다 — "데이터가 바뀌면 화면을 누가, 어떻게 따라오게 하는가." Vue 처럼 바인딩이 자동으로 책임지면 코드는 짧아지지만 흐름이 암묵적이고, React 처럼 네가 직접 명시하면 코드는 늘지만 흐름이 투명합니다. 둘 다 옳은 선택이고, 트레이드오프가 다를 뿐입니다.

Runnable 은 Vue 로 만들어졌습니다. 그래서 이 프로젝트에서는 바인딩(반응형)이 동기화를 책임집니다 — store 값이 바뀌면 화면과 지도가 알아서 따라옵니다(01·02 챕터에서 본 그대로). 우리가 React 였다면, 그 따라옴을 매번 손으로 명시해야 했을 겁니다. 어떤 프레임워크를 쓰느냐가 곧 "동기화의 책임을 누구에게 맡길 것인가"의 선택입니다.

05 / MENTAL MODEL

한 문장으로 정리

한 문장 멘탈 모델

Vue 가 MVVM 인 이유는 웹이라서가 아니라 반응형 양방향 바인딩을 채택했기 때문이고, React 가 MVVM 이 아닌 이유도 웹이라서가 아니라 그 바인딩을 일부러 버리고 단방향 흐름을 택했기 때문이다 — 패턴은 플랫폼이 아니라 설계 선택이 결정한다.
