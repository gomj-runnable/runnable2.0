On-Demand Install · Lazy Code-Split

설치를 누르는 그 순간
비로소 메모리에 올라오는 플러그인

목표는 명확합니다 — 사용자가 '설치'를 누르기(또는 해당 페이지로 이동하기) 전까지 그 기능의 코드는 네트워크로 받지도, 파싱하지도, 메모리에 올리지도 않는다. 설치 시점에 그때 청크를 받아 적용하고, 그 전까지 성능 비용은 0입니다. 이를 가능하게 하는 기술(코드 스플리팅 + 동적 import)과 Runnable plugins-ext/에 적용하는 구체적 절차를 정리합니다.

01 / CONCEPT

"설치형"의 정체 — 지연 코드 스플리팅

번들러(Vite)는 정적 import 은 메인 청크에 합치고, 동적 import() 는 별도 청크로 분리합니다. 분리된 청크는 그 함수가 실제로 호출될 때까지 네트워크 요청·파싱·실행이 일어나지 않습니다. "설치"란 결국 그 동적 import 를 처음 호출하는 행위입니다.

02 / GAP

지금은 왜 전부 메모리에 올라오나

현재 plugins-ext/ 는 모든 플러그인 컴포넌트를 정적으로 import 합니다. 그래서 미사용 플러그인도 첫 로드부터 메모리에 있습니다.

✗ 현재 (eager)

  • manifest 가 최상단에서 import SidewalkChip from './SidewalkChip.vue'
  • registry.ts 가 6개 매니페스트를 모두 정적 import
  • → 모든 컴포넌트 코드가 메인 청크에 포함
  • → 끄거나 안 쓰는 플러그인도 파싱·메모리 적재됨

✓ 목표 (lazy)

  • manifest 는 메타데이터만 정적, 컴포넌트는 loader: () => import(...)
  • registry 는 가벼운 manifest 만 모음 (컴포넌트 코드 미포함)
  • → 각 컴포넌트가 독립 청크로 분리
  • → 설치/렌더 시점에만 loader 호출 → 그때 적재
핵심 한 줄: manifest 파일의 최상단 컴포넌트 import 를 없애고, 동적 import 로더로 바꾸는 것이 전부입니다. 최상단 정적 import 가 하나라도 남으면 그 컴포넌트는 다시 eager 가 됩니다.
03 / HOW TO APPLY

Runnable 적용 절차 (5단계)

아래 변경만으로 "설치 전 0 비용 → 설치 시 로드" 가 성립합니다. 코드는 방향 예시이며 실제 타입·이름에 맞게 다듬어 쓰세요.

1 매니페스트 타입: 컴포넌트 → 로더

app/plugins-ext/types.ts
// component 즉시 참조를 지연 로더로 교체
export interface PluginManifest {
    id: string
    label: string
    description: string
    slot: PluginSlot
    defaultEnabled: boolean
    position?: ChipAnchor
    order?: number
-   component: Component                       // ✗ 즉시 = eager
+   loader: () => Promise<{ default: Component }>  // ✓ 호출 전엔 청크 미요청
}

2 각 매니페스트: 최상단 import 제거

app/plugins-ext/sidewalk/plugin.manifest.ts
- import { markRaw } from 'vue'
- import SidewalkChip from './SidewalkChip.vue'   // ✗ 이 줄이 eager의 원인
import type { PluginManifest } from '../types'

const manifest: PluginManifest = {
    id: 'sidewalk',
    label: '인도',
    description: '선택 지역의 인도를 지도에 표시합니다.',
    slot: 'chip',
    defaultEnabled: false,   // 설치형이면 기본 미설치 권장
    position: 'top-right',
+   loader: () => import('./SidewalkChip.vue')   // ✓ 설치 시 1회 fetch
}
export default manifest
registry.ts 는 그대로 둬도 됩니다. manifest 객체는 이제 컴포넌트 코드를 품지 않는 가벼운 메타데이터라, 정적 import 해도 무겁지 않습니다. 무거운 .vue 는 loader 뒤에 숨었습니다.

3 설치 상태 store: enabled → installed 영속화

app/plugins-ext/usePluginPrefs.ts (확장)
// 기존 isEnabled 흐름을 '설치됨' 의미로 사용/확장한다.
function isInstalled(plugin: PluginManifest): boolean {
    return prefs.value[plugin.id] ?? plugin.defaultEnabled
}

async function install(id: string) {
    prefs.value = { ...prefs.value, [id]: true }       // 낙관적 반영
    await $fetch('/api/me/feature-prefs', {
        method: 'PUT', body: { pluginId: id, enabled: true }
    })
}
async function uninstall(id: string) {
    prefs.value = { ...prefs.value, [id]: false }
    await $fetch('/api/me/feature-prefs', {
        method: 'PUT', body: { pluginId: id, enabled: false }
    })
}
설치 상태가 영속화돼야 재방문 시 설치한 것만 자동 로드되고, 나머지는 여전히 0 비용으로 남습니다.

4 호스트: 설치된 것만 async 컴포넌트로 렌더

app/plugins-ext/PluginSurfaceHost.vue (script)
import { defineAsyncComponent, computed } from 'vue'
import { usePluginSurfaces } from './usePluginSurfaces'

const { active, close } = usePluginSurfaces()

// active 가 바뀔 때만 loader 호출 → 그 순간 청크 fetch
const activeComponent = computed(() =>
    active.value ? defineAsyncComponent(active.value.loader) : null
)
<!-- template: 정적 component 대신 async 컴포넌트 -->
<component :is="activeComponent" />
chip 슬롯(MapOverlayAnchors 가 주입)도 동일하게, 설치된 chip 플러그인만 defineAsyncComponent(loader) 로 렌더하도록 바꿉니다. 설치 안 된 chip 의 loader 는 호출되지 않으므로 청크가 요청되지 않습니다.

5 설치 버튼: 그 클릭이 곧 로드 트리거

설정/스토어 화면 어디서든
const { isInstalled, install, uninstall } = usePluginPrefs()

function onInstallClick(plugin: PluginManifest) {
    // install() 로 설치 플래그 ON → 호스트의 computed 가 반응 →
    // defineAsyncComponent(loader) 가 처음 렌더되며 청크를 fetch
    install(plugin.id)
}
<!-- 미설치: 설치 버튼만, 코드 없음 / 설치됨: 적용 + 제거 가능 -->
<UButton v-if="!isInstalled(plugin)" @click="onInstallClick(plugin)">설치</UButton>
<UButton v-else @click="uninstall(plugin.id)">제거</UButton>
04 / PAYOFF

설치 전에 절약되는 것

미설치 상태에서 0이 되는 비용들입니다. 측정은 DevTools Network(청크 요청 유무)·Performance(스크립트 평가 시간)로 확인합니다.

네트워크

해당 청크 다운로드가 아예 발생하지 않음. 초기 페이지 전송량 감소.

파싱·컴파일

JS 엔진이 그 코드를 파싱/컴파일하지 않음 → 메인 스레드 시간 절약.

실행·초기화

모듈 top-level 실행, 의존 라이브러리 init, 반응성 등록이 안 일어남.

메모리

컴포넌트 정의·인스턴스·구독이 힙에 올라오지 않음 → 미설치 기능은 0 점유.

측정 팁: Network 탭에서 설치 클릭 직전엔 플러그인 청크(예: SidewalkChip-xxxx.js)가 안 보이다가, 클릭하는 순간 새 요청으로 나타나면 성공입니다.
05 / ADVANCED

한 발 더 — "외부 웹에서" 설치

위 1~5단계는 이미 내 빌드에 포함된 청크를 설치 시점에 로드합니다(=배포할 때 함께 빌드됨). "앱을 재배포하지 않고 외부에서 새 기능을 들여오는" 진짜 원격 설치를 원하면 한 단계 더 나아갑니다.

옵션 A · 원격 ESM 동적 import

외부 URL의 ESM 모듈을 import(/* @vite-ignore */ url) 로 런타임 로드. 가장 단순하지만 버전·호환·보안을 직접 책임져야 함.

옵션 B · Module Federation

독립 배포된 원격 번들을 런타임에 합성(②의 Gen 4). 공유 의존성(Vue 등) 협상이 핵심. 마이크로 프론트엔드급 인프라.

반드시 함께 갈 것

보안·신뢰: 외부 코드는 신뢰 불가 전제 → CSP(script-src) 정비, 서명/검수, 그리고 ②③에서 다룬 iframe·Worker 격리·권한 모델. 1st-party만이면 옵션 없이 1~5단계로 충분(YAGNI).

06 / CHECKLIST & GOTCHAS

적용 체크리스트와 주의점

  • 모든 manifest 에서 컴포넌트 최상단 정적 import 제거 — 하나라도 남으면 그 플러그인은 eager 유지
  • manifest 의 component 를 loader: () => import(...) 로 전환
  • 호스트(surface + chip)에서 설치된 것만 defineAsyncComponent 로 렌더
  • 설치 상태를 영속화(feature-prefs)하고, 재방문 시 설치분만 로드
  • Network 탭으로 설치 전 청크 미요청 → 설치 클릭 시 요청 발생 검증
  • 로딩 중 표시·실패 폴백: defineAsyncComponent({ loader, loadingComponent, errorComponent })
제거(uninstall) ≠ 메모리 완전 해제

한 번 로드된 JS 모듈은 브라우저 모듈 캐시에 남습니다. 제거는 컴포넌트 인스턴스·구독을 정리(언마운트)해 실행 비용을 멈추지만, 코드 자체를 힙에서 evict 하진 못합니다. 진짜 의미의 "0 비용"은 설치 전 상태에서만 성립 — 그래서 기본값을 미설치로 두는 게 중요합니다.

SSR / 하이드레이션

설치형은 본질적으로 클라이언트 동작입니다. 호스트 렌더를 <ClientOnly> 로 감싸거나 클라이언트에서 prefs 로드 후 마운트해 하이드레이션 불일치를 피하세요.

prefetch 충돌 주의

의도와 달리 미설치 청크를 미리 받아오지 않도록, 동적 import 에 불필요한 prefetch/preload 힌트를 붙이지 마세요(필요 시 빌드 설정에서 자동 prefetch 비활성).
