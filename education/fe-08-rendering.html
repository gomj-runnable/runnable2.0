Runnable · Frontend Lecture · 08

반응형은 공짜가 아니다
— 렌더링과 성능

Vue 의 반응형은 데이터가 바뀌면 화면이 알아서 따라온다는 강점을 줍니다. 하지만 '알아서'에는 비용이 숨어 있습니다. 이 챕터는 그 비용이 어디서 생기고, key · computed · 동적 import 로 어떻게 다스리는지를 다룹니다.

난이도 ★★★ 선행: 07 생명주기 키워드 rendering · performance
01 / WHY

편한 만큼 비용이 숨어 있다

반응형의 강점은 '알아서 다시 그림'이지만, 잘못 쓰면 '쓸데없이 자주 다시 그림'이 됩니다.

Vue 가 ref 나 reactive 로 관리하는 값이 바뀌면, 그 값에 의존하는 컴포넌트의 가상 DOM(Virtual DOM)을 다시 계산하고, 변경된 부분만 실제 DOM 에 반영합니다. 이 과정을 렌더 사이클이라고 부릅니다.

렌더 사이클은 빠릅니다 — 그러나 공짜는 아닙니다. 불필요한 재렌더가 쌓이면 버벅임이 생기고, 특히 지도처럼 무거운 캔버스와 함께하는 앱에서는 그 영향이 바로 체감됩니다. 이 챕터는 "안 해도 될 렌더를 안 하는" 세 가지 도구를 소개합니다.

02 / KEYS

v-for 의 key 는 신원증명서

key 가 없거나 index 면, 리스트가 바뀔 때 Vue 가 엉뚱한 DOM 을 재사용합니다.

나쁜 예 — key 없음 / index 사용

<!-- index 는 '몇 번째'이지 '누구'가 아님 -->
<li
  v-for="(route, i) in routes"
  :key="i"
>
  {{ route.name }}
</li>

앞에 항목이 추가·삭제되면 index 가 밀린다. Vue 는 '1번 항목이 같은 것'이라 착각하고 DOM 을 잘못 재사용한다.

좋은 예 — 안정적인 고유 id

<!-- routeId 는 항목의 신원 -->
<li
  v-for="route in routes"
  :key="route.routeId"
>
  {{ route.name }}
</li>

Runnable 의 ExplorePanel.vue 와 RouteListPanel.vue 는 실제로 :key="route.routeId" 를 씁니다.

key 는 Vue 에게 "이 항목이 그 항목과 같은 것"임을 알려주는 신원입니다. key 가 안정적이어야 Vue 가 DOM 을 올바르게 재사용(패치)하거나, 진짜 새 항목만 새로 그릴 수 있습니다. 배열 순서가 절대 안 바뀐다는 보장이 없다면 index 를 key 로 쓰지 마세요.

03 / COMPUTED vs METHOD

캐싱되는 값 vs 매번 도는 함수

computed 는 의존 값이 바뀌지 않으면 재계산하지 않습니다. 메서드는 매 렌더마다 실행됩니다.

나쁜 예 — 템플릿에서 메서드 호출

// 매 렌더마다 filteredRoutes() 가 다시 실행된다
function filteredRoutes() {
  return routes.value
    .filter(r => r.distance > minDist.value)
    .sort((a, b) => a.name.localeCompare(b.name))
}

<!-- 템플릿 -->
<li v-for="r in filteredRoutes()">

무관한 상태가 바뀌어 컴포넌트가 재렌더될 때마다 filter·sort 가 다시 돈다.

좋은 예 — computed 로 캐싱

// routes 나 minDist 가 바뀔 때만 재계산
const filteredRoutes = computed(() =>
  routes.value
    .filter(r => r.distance > minDist.value)
    .sort((a, b) => a.name.localeCompare(b.name))
)

<!-- 템플릿 -->
<li v-for="r in filteredRoutes">

의존하는 값(routes, minDist)이 바뀔 때만 재계산하고, 나머지 렌더에선 캐시를 돌려준다.

판단 기준: 파생값이면 computed, 이벤트 동작이면 method. "클릭했을 때 무언가를 한다"는 method, "이 목록의 필터 결과를 보여준다"는 computed 입니다. computed 를 method 처럼 호출하지 마세요 — 괄호가 없어야 캐시가 살아납니다.

04 / AVOID WORK

안 그려도 될 땐 안 그리게

핵심 기법들을 한 눈에 — 언제 무엇을 쓰는지.

안정적 key

v-for 의 key 에 서버가 부여한 고유 id 를 사용한다. DOM 패치 오류와 불필요한 재생성을 막는다.

언제: 리스트 렌더링 항상

computed 캐싱

파생값은 반드시 computed() 로. 의존 값이 바뀔 때만 재계산한다. 템플릿에서 괄호 없이 접근한다.

언제: 필터·정렬·포맷 등 파생값

동적 import

무거운 컴포넌트나 라이브러리를 필요한 시점에야 로드한다(코드 스플리팅). 초기 번들이 작아지고 첫 화면이 빨라진다.

언제: 무거운 서드파티·플러그인

v-once / v-memo

v-once — 딱 한 번만 렌더 후 고정. v-memo — 지정 배열이 바뀔 때만 갱신. 거의 안 바뀌는 정적 블록에 쓴다.

언제: 정적 헤더·법적 고지 등

deep watch 절제

{ deep: true } 는 큰 객체 전체를 재귀적으로 비교한다. 꼭 필요한 경우에만 쓰고, 가능하면 특정 속성만 watch 한다.

언제: 필요 최소한의 범위만

가상 스크롤

수천 개의 항목을 한꺼번에 렌더하지 않는다. 화면에 보이는 항목만 DOM 에 올리는 가상화(windowing) 라이브러리를 쓴다.

언제: 수백 개 이상의 리스트

동적 import 는 05 온디맨드(플러그인 트랙) 에서 다룬 코드 스플리팅과 같은 도구입니다. "플러그인을 설치 시점에야 로드한다"는 개념이 렌더링 성능에도 그대로 적용됩니다.

05 / IN RUNNABLE

지도라는 무거운 화면

Cesium 지도는 GPU 를 점유하는 무거운 캔버스입니다 — 전체를 다시 그리는 대신 필요한 것만 갱신합니다.

Runnable 의 성능 전략은 두 가지 원칙으로 요약됩니다. ① store 변경 → watch → 필요한 마커만 다시 그림(전체 컴포넌트 재렌더가 아님), ② 플러그인 컴포넌트는 열리는 순간 동적으로 로드(초기 번들에서 제외). 

// app/features/route-info/api/useRouteInfoSideeffect.ts
// 경로정보 목록 또는 로컬 경로정보 변경 시 마커 재렌더링
watch(
  [() => store.routeInfos.value, () => store.draftRouteInfos.value],
  () => renderRouteInfoMarkers(),   // 변경된 마커만 Cesium 에 반영
  { deep: true }               // 배열 내부까지 추적
)

여기서 deep: true 는 경로정보 배열 내부의 객체까지 추적해야 하기 때문에 씁니다. 다만 이 비용을 알기 때문에 watch 대상을 전체 store 가 아니라 routeInfos·draftRouteInfos 두 값으로만 좁혀 두었습니다. 

// app/plugins-ext/PluginSurfaceHost.vue (요약)
// active 플러그인의 component 는 이미 manifest 에 markRaw 로 등록된 컴포넌트
// PluginLauncher 는 enabled 플러그인만 v-for 로 버튼을 그림
<UButton
  v-for="p in surfacePlugins"
  :key="p.id"             <!-- 안정적인 플러그인 id -->
  @click="open(p.id)"
/>
<!-- 클릭 전까지 플러그인 컴포넌트 DOM 은 존재하지 않는다 -->
<component :is="active?.component" />

PluginSurfaceHost 는 active 가 null 이면 아무것도 그리지 않고, 열리는 순간에야 <component :is> 로 해당 컴포넌트를 마운트합니다. 지도 위 무거운 UI 를 "필요할 때만 존재하게" 하는 패턴입니다.

MENTAL MODEL

성능 최적화의 본질

한 문장 멘탈 모델

성능 최적화의 9할은 "계산을 줄이는 것"이 아니라 "안 해도 될 계산을 안 하는 것"이다 — 안정적 key 로 DOM 재생성을 막고, 캐싱되는 computed 로 불필요한 재계산을 막고, 필요할 때만 부르는 동적 import 로 초기 로드를 줄인다. Vue 의 반응형은 이미 최소 업데이트를 한다 — 우리가 할 일은 "힌트"를 올바르게 주는 것뿐이다.

QUIZ / 이해도 체크

학습 완료 퀴즈

4문항 전부 맞히면 이 챕터가 학습 완료로 기록됩니다.

  1. v-for 에서 :key="index" 를 사용했을 때 발생할 수 있는 문제는?

    • a) 브라우저가 key 속성을 지원하지 않아 렌더가 실패한다
    • b) 리스트 앞에 항목이 추가·삭제되면 index 가 밀려, Vue 가 엉뚱한 DOM 을 재사용해 화면이 어긋날 수 있다
    • c) index 는 서버와 동기화가 안 되어 네트워크 오류가 난다
    • d) computed 가 캐시를 무효화한다

  2. 같은 연산을 computed 와 method 로 각각 템플릿에서 사용할 때 차이는?

    • a) computed 는 매 렌더마다 재실행되지만, method 는 한 번만 실행된다
    • b) 둘 다 매 렌더마다 재실행되므로 차이가 없다
    • c) computed 는 의존 값이 바뀔 때만 재계산하고 결과를 캐싱하지만, method 는 컴포넌트가 렌더될 때마다 다시 실행된다
    • d) method 는 reactive 에만 반응하고, computed 는 ref 에만 반응한다

  3. watch 에 { deep: true } 를 쓸 때 주의해야 하는 이유는?

    • a) deep watch 는 Vue 3 에서 지원이 중단됐다
    • b) 배열·객체 내부까지 재귀적으로 비교하므로 큰 객체에 적용하면 비교 비용이 커진다
    • c) deep: true 는 computed 를 무효화시킨다
    • d) SSR 환경에서만 동작하므로 클라이언트 렌더링에서는 쓸 수 없다

  4. Runnable 에서 플러그인 컴포넌트가 클릭 전까지 DOM 에 존재하지 않는 이유는?

    • a) 플러그인은 서버에서만 렌더되기 때문이다
    • b) PluginSurfaceHost 가 active 값이 null 일 때 아무것도 마운트하지 않고, 클릭 시점에야 <component :is> 로 마운트하기 때문이다
    • c) v-for 의 key 가 없어서 Vue 가 렌더를 건너뛰기 때문이다
    • d) computed 가 null 을 반환해 렌더를 막기 때문이다
