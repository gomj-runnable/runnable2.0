Runnable · Frontend Lecture · 02

반응형을 한 상자에 묶다
— 컴포저블과 use*

앞 챕터의 ref·computed·watch 는 낱개 부품입니다. 그 부품들을 모아 "상태 + 그 상태를 다루는 함수"를 한 함수에 담아 재사용하는 단위가 컴포저블입니다. 이름 앞의 use 는 단순한 관례가 아니라, Vue·Nuxt 가 부여한 세 겹의 약속입니다 — 이 챕터에서 그 정체를 풉니다.

난이도 ★★☆ 선행: 01 반응형 키워드 composable · use*
01 / WHAT

컴포저블 = 상태를 가진 함수

보통 함수는 값을 받아 값을 돌려주고 끝납니다. 컴포저블은 자기만의 반응형 상태를 들고, 그 상태가 바뀌면 화면이 따라 갱신됩니다.

그냥 함수 — 기억이 없다

function add(a, b) {
  return a + b   // 호출하면 끝, 상태 없음
}

입력 → 출력. 화면과도, 생명주기와도 무관합니다.

컴포저블 — 살아있는 상태

function useCounter() {
  const count  = ref(0)              // 반응형 상태
  const double = computed(() => count.value * 2)
  const increment = () => { count.value++ }  // 바꾸면 화면 자동 갱신
  return { count, double, increment }
}

상태·파생값·동작을 한 상자에 담아 어디서든 const { count } = useCounter() 한 줄로 재사용.

진짜 가치는 로직 재사용입니다. "마우스 추적", "경로 초안 관리" 같은 로직을 컴포저블 하나에 캡슐화하면 — 상태 선언, 이벤트 등록, 그리고 컴포넌트가 사라질 때의 정리(onUnmounted)까지 한 곳에 담겨 여러 컴포넌트가 레고 블록처럼 끼워 씁니다. React 를 안다면 커스텀 훅과 사실상 같은 개념입니다.

02 / THREE MEANINGS

use 가 포개고 있는 세 겹

use* 는 그냥 이름 규칙이 아닙니다. Vue 의 관례 위에 Nuxt 가 두 겹의 약속을 더 얹은 신호입니다.

① Vue 의 관례

안에서 ref·computed·watch·onMounted 같은 반응성·생명주기 도구를 쓰는 함수라는 표식. 단순 유틸과 시각적으로 구분하려는 합의된 접두사입니다.

의미: "이건 컴포저블이다"

② Nuxt auto-import

app/composables/ 안에 use* 로 시작하는 함수를 두면 import 없이 전역에서 쓸 수 있게 Nuxt 가 자동 등록합니다.

특권: import 한 줄도 생략

③ setup 컨텍스트 제약

useRoute·useRuntimeConfig·useState 등은 setup·plugin·middleware 안에서 동기적으로 호출해야 합니다. await 뒤나 콜백 안에서 부르면 인스턴스 컨텍스트를 잃습니다.

제약: 호출 타이밍이 정해져 있다 
// ❌ await 뒤 → 컨텍스트 유실, 경고 발생
const data   = await fetch(...)
const config = useRuntimeConfig()

// ✅ setup 최상단에서 동기적으로
const config = useRuntimeConfig()
const data   = await fetch(...)
03 / SSR SAFETY

useState 는 "안 섞이게" 막는 장치다

흔한 오해 하나를 먼저 깹니다 — useState 는 사용자별로 다르게 보여주는 기능이 아니라, 사용자끼리 안 섞이게 막는 SSR 안전장치입니다.

모듈 스코프 ref — 사고

// 서버 1대가 요청 100개를 처리
const draft = ref([])   // 모듈 전역
// → 모든 요청이 같은 메모리 공유
// → A 가 만든 경로가 B 화면에 보임

요청 간 상태 오염(cross-request leak). SSR 에서 가장 흔한 함정.

useState — 안전

// 요청마다 격리된 상태 박스를 발급
const draft = useState('route.draft', () => [])
// → A 의 상태와 B 의 상태가 안 섞임
// → 서버→클라 직렬화·하이드레이션

요청별 격리 + 서버에서 만든 상태를 클라이언트로 이어줌.

그럼 "사용자별로 다른 데이터"는 누가 하나요? — 그건 별개의 레이어입니다. 인증/세션이 누구인지 식별하고, DB 조회(보통 useAsyncData 안의 fetch)가 그 사용자의 데이터를 가져옵니다. useState 는 그렇게 가져온 값을 요청 안에서 안전하게 담아두는 그릇일 뿐입니다.

04 / IN RUNNABLE

우리 코드의 use* 는 전부 컴포저블

Runnable 은 use* 를 책임별로 갈라 씁니다. 이름만 봐도 그게 상태인지, 동작인지, 부수효과인지 읽힙니다.

useXxxStore

useState + computed + 동기적 mutation. 앱 전역에서 공유하는 순수 상태 컨테이너.

예: useRouteInfoStore

useXxxAction

사용자 인터랙션의 진입점. 클릭·제출 같은 행위를 받아 store 와 sideeffect 를 엮습니다.

예: useRouteDrawAction

useXxxSideeffect

store 를 들고 바깥세계와 부딪히는 자리. Cesium 렌더·$fetch·watch 등 생명주기 자원.

예: useRouteInfoSideeffect

즉 이 코드베이스에서 use 는 "auto-import 되는, setup 컨텍스트에 묶인, 책임이 분리된 반응형 로직 단위"라는 합의된 신호입니다. 다음 챕터(MVVM)에서 이 store 가 어떻게 이미 ViewModel 인지로 이어집니다.

MENTAL MODEL

한 문장으로

한 문장 멘탈 모델

컴포저블은 반응형 상태와 로직을 한 상자에 담아 재사용하는 함수이고, use* 는 그 위에 ① Vue 의 컴포저블 관례 + ② Nuxt 의 auto-import + ③ setup 컨텍스트 제약이 포개진 신호다. useState 의 격리는 개인화가 아니라 요청끼리 안 섞이게 막는 안전장치다.

  1. 일반 함수와 구분되는 컴포저블의 핵심은?

    • a) 매개변수를 받아 값을 반환하고 바로 끝난다
    • b) ref 등 반응형 상태를 갖고, 그 변화가 화면에 자동 반영된다
    • c) 항상 import 를 명시해야만 쓸 수 있다
    • d) 오직 서버에서만 실행된다

  2. app/composables/ 의 use* 함수가 Nuxt 에서 누리는 것은?

    • a) 자동으로 결과가 캐싱된다
    • b) import 없이 어디서나 호출 가능(auto-import)
    • c) 서버에서만 동작한다
    • d) 반드시 .vue 파일 안에서만 정의해야 한다

  3. useState(key, init) 가 SSR 에서 보장하는 것은?

    • a) 로그인 사용자별로 다른 개인화 데이터를 자동 생성
    • b) 모든 요청이 같은 전역 메모리를 공유
    • c) 요청마다 격리된 상태 + 서버→클라 하이드레이션
    • d) 데이터베이스를 자동으로 연결

  4. useRoute·useRuntimeConfig 같은 Nuxt 컴포저블을 호출해야 하는 위치는?

    • a) 어디서든, 콜백 안이나 await 뒤도 무방
    • b) setup·plugin·middleware 안에서 동기적으로
    • c) 오직 서버 API 핸들러 안에서만
    • d) 전역 모듈 스코프에서만
