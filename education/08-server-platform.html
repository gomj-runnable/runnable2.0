Server Platform Track · 실무 연결

낮에 만드는 GIS 서버가
두 번째 훈련장이다

GeoServer 같은 GIS 서버는 업계에서 가장 확장 구조가 잘 짜인 소프트웨어 중 하나입니다. 데이터 소스·출력 포맷·서비스가 전부 플러그인으로 꽂히죠. 즉 ④에서 본 프론트엔드 plugins-ext 사다리를 서버 쪽에서 똑같이 오를 수 있다는 뜻입니다. 이 문서는 네 실무를 "GIS 기능 개발"에서 멈추지 않고 플랫폼 역량으로 전환하는 가이드입니다.

01 / TWO TRAINING GROUNDS

같은 근육, 두 무대

프론트와 서버는 표면이 다르지만, 기르는 역량은 하나입니다 — 확장 가능한 판을 설계하는 능력.

무대 A · 프론트엔드

Runnable · plugins-ext

  • 슬롯에 UI 모듈을 꽂는 호스트
  • 매니페스트 · registry · prefs
  • 브라우저 런타임 · 동적 로딩
  • 사용자가 보는 확장
+

무대 B · 서버

MapPrime GisServer

  • 확장점에 데이터·포맷·서비스를 꽂는 호스트
  • SPI · 모듈 로딩 · 서비스 레지스트리
  • JVM/서버 런타임 · OGC 프로토콜
  • 개발자가 쓰는 확장
두 무대가 합쳐지면 → "서버와 프론트 양쪽의 확장 모델을 다 아는 플랫폼 엔지니어". 한국에서 매우 희소하고, ⑥ 한계 문서에서 말한 "벽이 무너질 때 가장 먼저 준비된 사람"의 정확한 정의입니다.
02 / FEATURE vs ARCHITECTURE

둘 다 한다면, 의식적으로 '구조'를 만져라

네가 기능도 확장 구조도 둘 다 맡을 수 있다고 했죠. 같은 일이라도 어느 모자를 쓰느냐가 직군을 가릅니다.

기능 모자 · GIS 개발자

기능 작업이 주는 것

  • 지리공간 도메인 깊이 (투영·타일·공간쿼리)
  • OGC 표준(WMS/WFS/WMTS) 숙련
  • 성능·정확도 감각
  • → 깊지만, 여기 머물면 대체 가능한 기능 개발자

구조 모자 · 플랫폼 개발자

구조 작업이 주는 것

  • 경계 설계 — 무엇을 SPI로 열고 무엇을 숨길지
  • 확장점·계약·버저닝 — 남이 꽂을 판을 만든다
  • 격리·신뢰·배포 사고
  • → 희소하고, 플랫폼 엔지니어로 자라는 길
핵심 — 기능을 짜더라도 매번 "이걸 어떻게 확장 가능하게 만들까?"를 한 번 더 묻는 습관. 그 한 질문이 같은 코드를 "기능 구현"에서 "플랫폼 설계"로 바꿉니다. (단, 남발은 과설계 — 05/§5의 YAGNI 균형)
03 / SERVER LADDER

서버판 성장 사다리 (S1~S4)

④ 프론트 로드맵의 L1~L4와 정확히 짝지어집니다. 각 단계의 gate를 통과하면 ⑦ 학습 로그에 기록하세요.

S1 소비자 → 한 확장 끝까지 읽기 ↔ L1 · 첫 chip
  • 기존 확장 하나(예: 한 DataStore 또는 output format)를 요청 진입 → 응답까지 추적
  • 호스트가 모듈을 어떻게 발견·등록하는지 (SPI / 서비스 로더) 파악
  • OGC 요청 한 종류(GetMap 등)의 전체 경로를 그려보기
Gate  새 요청이 들어와 응답이 나가기까지, 한 확장이 어디서 어떻게 꽂히는지 그림으로 설명할 수 있다.
S2 새 확장 하나를 꽂는다 ↔ L2 · 상태 반응 패널
  • 코어를 건드리지 않고 새 출력 포맷 / 새 데이터 소스 / 새 오퍼레이션을 추가
  • 기존 확장점(인터페이스)을 구현해 레지스트리에 등록
  • 설정·토글로 켜고 끄는 경로 이해
Gate  코어 코드를 수정하지 않고 확장점만으로 새 기능 하나를 서버에 추가한다.
S3 확장점 자체를 설계한다 ↔ L3 · 계약 설계
  • 새 SPI / 플러그인 인터페이스를 정의 — 남이 꽂을 자리를 연다
  • 무엇을 공개(public contract)하고 무엇을 내부로 숨길지 결정
  • 버저닝·하위호환·deprecation 전략 (계약을 깨지 않고 진화)
  • 타입/인터페이스로 계약 강제, 예제 모듈로 검증
Gate  다른 개발자가 네 코어 내부를 몰라도, 네가 만든 계약만 보고 모듈을 작성할 수 있다.
S4 격리 · 신뢰 · 배포 ↔ L4 · 격리 PoC
  • 신뢰 불가 모듈 가정 — 리소스 제한·타임아웃·샌드박스(클래스로더 격리 등)
  • 권한 모델 — 모듈이 접근 가능한 능력을 명시적으로 제한
  • 배포·버전 — 모듈 독립 배포, 서명·검수, semver 계약
  • "언제 도입할지" 판단 — 사내 1st-party뿐이면 과설계(YAGNI)
Gate  외부 모듈을 안전하게 받는다면 필요한 격리·권한·배포를 설계하고, 핵심 한 가지를 PoC로 증명한다.
04 / THE BRIDGE

전이되는 개념 — 서버 ↔ 프론트

무대가 달라도 같은 패턴입니다. 이 표가 "왜 두 일이 같은 근육인지"의 증거입니다.

보편 역량GIS 서버프론트 · plugins-ext
host ↔ plugin 계약DataStore / Service SPIPluginManifest
확장점(자리 열기)output format · operation 확장슬롯 (chip·panel·dashboard)
레지스트리·발견SPI / ServiceLoader 모듈 로딩registry.ts
공개 API 버저닝SPI / REST 계약 안정성PluginContext (④ L3)
격리·권한클래스로더 격리·리소스 제한iframe · Worker 격리
표준 준수OGC 프로토콜 (WMS/WFS…)웹 표준 · 접근성
지연·성능모듈 lazy 로딩·캐시·타일동적 import (⑤ 온디맨드)
경계 설계·계약·버저닝·격리는 직군이 아니라 사고방식입니다. 그래서 서버에서 길러도 프론트로, 프론트에서 길러도 서버로 그대로 따라옵니다 — 네가 양쪽을 다 하므로 전이가 두 배로 빨라집니다.
05 / HABITS

플랫폼 개발자로 자라는 일습관

거창한 프로젝트가 아니라, 매일의 작업에 끼워 넣는 질문들이 직군을 바꿉니다.

  • ?
    기능 요청을 받으면 먼저 묻기 — "이건 일회성 기능인가, 반복될 패턴(확장점)인가?" 패턴이면 확장점으로 빼고, 일회성이면 그냥 짠다(YAGNI).
  • 1
    구현보다 인터페이스(SPI)를 먼저 그린다 — 계약 우선. "이 모듈이 받아야 할 입력/출력 모양"부터 확정.
  • 2
    무엇을 공개/은폐할지 의식적으로 결정. 내부 구현 클래스를 공개 API로 새어 나가게 두지 않는다 (그러면 버저닝 불가).
  • 3
    변경 전 묻기 — "이 변경이 기존 모듈을 깨나?" 깨면 semver·deprecation 경로를 둔다.
  • 4
    "남이 이걸 어떻게 작성하지?" — 예제 모듈·문서·스캐폴딩을 남긴다. DX 없으면 아무도(미래의 나 포함) 못 쓴다.
  • 5
    격리 가정 — 모듈 하나가 서버 전체를 멈추지 않게 타임아웃·리소스 경계를 의식. (필요 시점에만 — 과설계 금지)
06 / PITFALLS

GIS 서버에서 자주 빠지는 함정

대부분 "기능만 보고 구조를 안 봐서" 또는 "구조를 너무 일찍 봐서" 생깁니다.

✗ 표준 준수에만 매몰

OGC 스펙 맞추기에만 집중하고 확장 구조를 안 본다. → 기능 개발자에 머묾. 스펙은 토대, 구조가 성장축.

✗ 코어에 하드코딩

새 포맷·소스를 코어에 직접 분기로 추가. 다음 요청마다 코어를 또 수정. → 확장점으로 빼라.

✗ 확장점 과설계

구현은 1개뿐인데 추상 레이어를 5겹 쌓음. YAGNI — 두 번째 구현이 보일 때 추상화하라.

✗ 내부 구현 누출

내부 클래스·필드를 공개 API로 노출. 다음 리팩터링에서 모든 모듈이 깨짐. → 좁고 안정적인 표면만.

✗ 격리 무시

무겁거나 실패하는 모듈 하나가 서버 전체를 다운. → 경계·타임아웃·리소스 제한(필요 시점에).

✗ DX 방치

확장 작성법이 머릿속에만. 예제·문서 없으면 팀의 다른 개발자가 확장을 못 만듦 = 판이 죽음.

    • a) 서버가 프론트보다 더 쉽기 때문
    • b) 데이터·포맷·서비스가 전부 플러그인으로 꽂히는 확장 구조라, 프론트 plugins-ext 사다리를 서버에서도 똑같이 오를 수 있어서
    • c) 서버는 OGC 표준만 지키면 끝이라서
    • d) 프론트엔드를 더는 안 해도 되기 때문

  2. 서버 사다리에서 "코어를 건드리지 않고 새 출력 포맷·데이터 소스를 추가"하는 단계는?

    • a) S1 — 한 확장 끝까지 읽기
    • b) S2 — 새 확장 하나를 꽂는다
    • c) S3 — 확장점 자체를 설계한다
    • d) S4 — 격리·신뢰·배포

  3. 개념 다리(BRIDGE) 표에서 GIS 서버의 SPI 와 짝지어지는 프론트 plugins-ext 개념은?

    • a) iframe · Worker 격리
    • b) 동적 import
    • c) PluginManifest (host ↔ plugin 계약)
    • d) 웹 표준 · 접근성

  4. 이 문서가 말하는 "확장점 과설계" 함정을 피하는 원칙은?

    • a) 모든 기능을 처음부터 추상 레이어 5겹으로 감싼다
    • b) OGC 스펙 준수에만 집중한다
    • c) YAGNI — 두 번째 구현이 보일 때 추상화하고, 일회성이면 그냥 짠다
    • d) 내부 구현 클래스를 공개 API로 노출한다
