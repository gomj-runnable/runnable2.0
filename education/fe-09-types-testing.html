Runnable · Frontend Lecture · 09

에러를 미리 잡는 두 그물
— 타입과 테스트

버그를 사용자가 만나기 전에 잡는 방법은 두 가지입니다 — 타입 시스템이라는 정적 그물과 테스트라는 동적 그물. 이 챕터는 TypeScript + Zod 가 경계를 지키는 법과, 컴포저블을 함수처럼 테스트하는 Vitest 패턴을 Runnable 실제 코드로 살펴봅니다.

난이도 ★★★ 선행: 08 렌더링·성능 키워드 types · testing 마지막 챕터
01 / WHY

버그를 왼쪽으로 당겨라

런타임에 터질 에러를 컴파일·테스트 단계로 앞당기는 것(shift-left)이 핵심 전략입니다.

컴파일 타임

TypeScript 타입 검사 — 에디터와 빌드 단계. 사용자는 아직 아무것도 모른다.

테스트 실행

Vitest 단위 테스트 — CI 파이프라인. 의도한 동작이 깨지면 머지가 막힌다.

런타임

사용자 앞에서 터지는 에러 — 이 단계까지 오면 UX 손상 + 신뢰 손실이다.

타입은 정적 그물 — "이 함수에 문자열을 넣으면 안 된다"는 사실을 코드 수준에서 강제합니다. 테스트는 동적 그물 — "경로를 선택하면 슬라이드오버가 열려야 한다"는 의도를 코드로 박제합니다. 둘은 경쟁이 아니라 서로 다른 층의 버그를 막는 두 방어선입니다.

02 / VUE + TS

타입이 붙은 반응형

01~06 챕터에서 배운 ref·defineProps·emit에 타입을 입히면 IDE 자동완성과 컴파일 에러가 공짜로 따라옵니다.

타입 없음 — any 지뢰밭

// 타입 없는 ref: IDE 도움 없음
const routes = ref([])

// 타입 없는 props: 오타도 컴파일 에러 없음
const props = defineProps({
  selectedRouteId: String,
  routes: Array
})

잘못된 형태를 넘겨도 에러가 없다. 버그는 런타임에야 등장한다.

타입 명시 — 컴파일 타임 보호막

// shared/types/route.ts 의 SavedRoute 로 제한
import type { SavedRoute } from '#shared/types/route'

const routes = ref<SavedRoute[]>([])

// RouteListPanel.vue — 실제 Runnable 코드
const props = defineProps<{
  routes: SavedRoute[]
  selectedRouteId: string | null
  currentUserId?: string | null
}>()

const expandedIds = ref<Set<string>>(new Set())

잘못된 타입을 넘기면 에디터가 빨간 줄로 표시한다. 런타임 전에 잡힌다.

defineProps<T>()는 Props 인터페이스를 제네릭으로 받아 런타임 선언 없이 타입을 부여합니다. ref<T>()는 초기값에서 타입을 추론할 수 없을 때([], null) 명시적으로 제네릭을 붙입니다. computed 의 반환 타입은 Vue가 추론하지만, 복잡한 경우 computed<RouteInfo[]>(() => ...)로 직접 선언할 수 있습니다.

03 / ZOD AT THE BORDER

경계에서 한 번 검증한다

서버 응답·외부 입력은 믿을 수 없습니다. Zod 스키마로 시스템 경계에서 한 번 parse하면, 통과한 뒤로는 TypeScript 타입이 보장됩니다.

Runnable 의 shared/schemas/에는 API 요청·응답을 검증하는 Zod 스키마가 모여 있습니다. routeInfo.schema.ts를 예로 보겠습니다. 

// shared/schemas/routeInfo.schema.ts — 실제 파일
import { z } from 'zod'
import { geoJsonPointSchema } from './route.schema'

export const createRouteInfoSchema = z.object({
  name: z.string()
    .min(1, '장소명을 입력해주세요')
    .max(100, '장소명은 최대 100자까지 가능합니다'),
  description: z.string()
    .min(1, '설명을 입력해주세요')
    .max(500, '설명은 최대 500자까지 가능합니다'),
  geom: geoJsonPointSchema   // GeoJSON Point — [lng, lat] 또는 [lng, lat, elevation]
})

route.schema.ts에는 POI, 구간, 경로 생성을 위한 스키마도 있습니다. 

// shared/schemas/route.schema.ts (발췌)
export const geoJsonPointSchema = z.object({
  type: z.literal('Point'),
  coordinates: z.array(z.number()).min(2).max(3)
})

export const poiSchema = z.object({
  name: z.string().min(1),
  type: z.enum(['HOSPITAL', 'CROSSWALK', 'WATER']),
  geom: geoJsonPointSchema,
  attribute: z.record(z.string(), z.unknown()).optional()
}) satisfies z.ZodType<PoiCreateInput>

export const createRouteSchema = z.object({
  title: z.string()
    .min(1, '경로 제목을 입력해주세요')
    .max(255, '경로 제목은 최대 255자까지 가능합니다'),
  description: z.string().optional(),
  distance: z.number().nonnegative().optional(),
  // ...
})

satisfies z.ZodType<T> 패턴이 중요합니다 — 스키마가 TypeScript 타입과 일치함을 컴파일 타임에 보장합니다. 스키마가 타입보다 좁거나 넓으면 즉시 에러가 납니다. 한번 parse를 통과하면 내부에서는 any를 쓸 필요가 없습니다 — Zod가 뱉은 값은 이미 TypeScript 타입입니다.

핵심 구분

TypeScript 타입은 컴파일 타임 약속 — 빌드 결과물에는 흔적조차 없습니다. Zod는 런타임 검문소 — 외부에서 들어오는 데이터는 실행 중에 검사해야 합니다. API 응답처럼 컴파일러가 볼 수 없는 데이터에는 둘 다 필요합니다.

04 / TESTING COMPOSABLES

컴포저블은 함수라 테스트가 쉽다

02 챕터에서 로직을 컴포저블(상태 + 함수)로 묶었기 때문에, Vue 컴포넌트를 마운트하지 않고도 함수를 직접 호출해 단위 테스트할 수 있습니다.

Runnable 은 테스트 러너로 vitest를 사용합니다. useOverlayContext.test.ts가 좋은 예입니다 — 화면 없이, 컴포저블에 입력을 주고 출력 상태를 단언합니다. 

// app/widgets/map-page/model/__tests__/useOverlayContext.test.ts (발췌)
import { describe, it, expect, vi, beforeEach } from 'vitest'
import { ref, nextTick } from 'vue'
import { useOverlayContext } from '~/widgets/map-page/model/useOverlayContext'
import { MapOverlayContextEnum } from '#shared/types/map-overlay-context.enum'

// Arrange — 필요한 의존성을 ref 로 만들어 주입
describe('useOverlayContext', () => {
  let opts: any
  beforeEach(() => {
    opts = {
      activeNav: ref('탐색'),
      sectionDraft: ref(null),
      selectedRouteId: ref<string | null>(null),
      exploreSelectedRouteId: ref<string | null>(null),
      routeInfoStore: { isAddingRouteInfo: ref(false), /* ... */ },
      routeInfoEffect: { cancelAdding: vi.fn() }
    }
  })

  it('초기값 — overlayContext = NONE', () => {
    // Act
    const { overlayContext } = useOverlayContext(opts)
    // Assert
    expect(overlayContext.value.key).toBe(MapOverlayContextEnum.NONE.key)
  })

  it('그리기 탭 + sectionDraft 있음 → DRAWING', () => {
    opts.activeNav.value = '그리기'
    opts.sectionDraft.value = { routeId: 'x' }
    const { overlayContext } = useOverlayContext(opts)
    expect(overlayContext.value.key).toBe(MapOverlayContextEnum.DRAWING.key)
  })

  it('overlayContext 활성→비활성 전환 시 routeInfo 정리', async () => {
    opts.activeNav.value = '목록'
    opts.selectedRouteId.value = 'r-1'
    opts.routeInfoStore.isAddingRouteInfo.value = true
    useOverlayContext(opts)
    await nextTick()

    opts.activeNav.value = '탐색'       // 비활성으로 전환
    opts.selectedRouteId.value = null
    await nextTick()

    expect(opts.routeInfoEffect.cancelAdding).toHaveBeenCalled()
  })
})

패턴을 보면 항상 Arrange → Act → Assert 세 단계입니다. 컴포저블을 호출하고(Act), 반환된 반응형 값이나 함수 호출 여부를 단언합니다(Assert). nextTick()은 watch 콜백이 비동기로 실행되기 때문에 기다리는 것입니다.

useRouteSelectionFlow.test.ts는 더 복잡한 시나리오를 보여줍니다 — vi.hoisted로 모듈 mock 을 선언하고, 경로 선택 시 슬라이드오버가 열리는지, 수정 모드 전환이 올바르게 일어나는지를 함수 호출로만 검증합니다. 화면을 렌더링하지 않아도 동작 명세를 검증할 수 있는 것이 컴포저블 분리의 핵심 이점입니다.

05 / IN RUNNABLE

Zod 도메인 타입 + 컴포저블 테스트 두 축

Runnable 에서 타입과 테스트는 각각 이렇게 자리를 잡고 있습니다.

shared/types/

RouteInfoCreateInput / SavedRouteInfo 처럼 CreateInput · Saved 계층으로 타입을 나눕니다. 생성 전 / 생성 후 형태가 명확히 구분되어 잘못된 조합이 타입 에러로 잡힙니다.

타입 → 컴파일 타임 약속

shared/schemas/

Zod 스키마가 API 경계를 지킵니다. satisfies z.ZodType<T>로 스키마와 TypeScript 타입을 동기화합니다. 형식 오류는 parse 직후 명확한 메시지로 뜹니다.

Zod → 런타임 검문소

__tests__/

위젯별 컴포저블 단위 테스트. Vitest + vi.fn() mock 으로 의존성을 격리하고 입력 → 상태 변화 → expect 를 검증합니다.

테스트 → 동작 명세 박제

shared/types/routeInfo.ts를 보면 RouteInfoCreateInput(생성 입력)과 SavedRouteInfo(DB 저장 결과)가 계층으로 나뉩니다. "저장되지 않은 핀에 routeInfoId를 읽으려 했다"는 버그는 이 구분만으로도 컴파일 타임에 차단됩니다. Zod createRouteInfoSchema는 API 요청이 이 형태를 만족하는지 런타임에 한 번 더 확인합니다.

MENTAL MODEL

두 그물의 역할

한 문장 멘탈 모델

타입은 "있을 수 없는 상태를 코드로 막는 것", 테스트는 "의도한 동작을 코드로 박제하는 것". 둘은 경쟁이 아니라 안과 밖에서 같은 버그를 막는 두 그물이다 — 타입은 데이터의 형태를 강제하고, 테스트는 데이터의 흐름을 보장한다.

QUIZ / 이해도 체크

학습 완료 퀴즈

4문항 전부 맞히면 이 챕터가 학습 완료로 기록됩니다.

  1. TypeScript 타입과 Zod 스키마의 역할 구분으로 올바른 것은?

    • a) TypeScript 타입은 런타임에 외부 데이터를 검증하고, Zod 는 컴파일 타임에만 동작한다
    • b) TypeScript 타입은 컴파일 타임 약속이고, Zod 는 런타임 검문소다 — API 응답처럼 컴파일러가 볼 수 없는 데이터에는 둘 다 필요하다
    • c) Zod 를 쓰면 TypeScript 타입은 필요 없다
    • d) TypeScript 타입은 서버에서만, Zod 는 클라이언트에서만 사용한다

  2. Vue 컴포넌트에서 defineProps<{ routes: SavedRoute[] }>() 처럼 제네릭을 쓰는 이유는?

    • a) 성능 최적화를 위해 Vue 가 내부적으로 캐싱하도록 힌트를 준다
    • b) 런타임에 배열 길이를 자동으로 제한한다
    • c) 잘못된 타입을 넘기면 에디터와 빌드 단계에서 즉시 에러가 나, 런타임 전에 버그를 잡을 수 있다
    • d) 서버에서 props 를 자동으로 직렬화해 전송한다

  3. Runnable 의 useOverlayContext.test.ts에서 await nextTick()을 쓰는 이유는?

    • a) 서버 API 응답을 기다리기 위해
    • b) watch 콜백이 비동기로 실행되므로, 상태 변경 후 콜백이 실제로 호출됐는지 확인하려면 한 틱을 기다려야 한다
    • c) Vitest 가 동기 코드를 병렬 실행하기 때문에
    • d) Vue DOM 렌더링 완료를 기다리기 위해 — 화면 마운트 없이는 필요 없다

  4. 컴포저블을 컴포넌트에서 분리해 독립 함수로 만들면 테스트 측면에서 어떤 이점이 있는가?

    • a) 화면을 렌더링하지 않아도 함수를 직접 호출해 로직을 검증할 수 있어, 테스트가 빠르고 단순해진다
    • b) TypeScript 타입 검사가 자동으로 비활성화된다
    • c) Zod 스키마 없이 API 응답을 바로 사용할 수 있다
    • d) Vitest 대신 Jest 를 써야 한다
