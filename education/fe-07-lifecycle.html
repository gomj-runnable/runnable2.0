Runnable · Frontend Lecture · 07

켜질 때 준비하고, 꺼질 때 치운다
— 생명주기와 정리

컴포넌트는 화면에 나타나고, 살아 있는 동안 동작하고, 사라질 때 자원을 돌려줍니다. 이 챕터는 Vue의 생명주기 훅이 언제 실행되는지, 그리고 왜 정리(cleanup)가 의무인지를 Runnable 의 지도·뷰어·sideeffect 코드로 직접 확인합니다.

난이도 ★★☆ 선행: 06 컴포넌트 통신 키워드 lifecycle · cleanup
01 / WHY

컴포넌트에는 수명이 있다

화면에 나타나고 → 갱신되고 → 사라지는 흐름. 켜질 때 잡은 자원은 꺼질 때 반드시 놓아야 합니다.

사용자가 지도 페이지에 들어오면 Cesium viewer 가 초기화되고, 이벤트 리스너가 등록되고, watch 가 상태를 감시하기 시작합니다. 그런데 사용자가 다른 페이지로 이동하면 어떻게 될까요? 컴포넌트는 사라졌지만, 정리하지 않은 자원들은 메모리 어딘가에 계속 살아 있습니다.

정리 없음 — 누수 발생

onMounted(() => {
  // 이벤트 리스너 등록
  window.addEventListener('resize', onResize)

  // 타이머 시작
  timer = setInterval(tick, 1000)

  // viewer 생성
  viewer = new Cesium.Viewer(...)
})

// onUnmounted 없음 → 컴포넌트가 사라져도
// 리스너·타이머·viewer 는 계속 실행된다

페이지를 여러 번 드나들수록 리스너가 중복 등록되고 메모리가 쌓인다. 결국 느려지거나 오작동한다.

onUnmounted 에서 정리

onMounted(() => {
  window.addEventListener('resize', onResize)
  timer = setInterval(tick, 1000)
  viewer = new Cesium.Viewer(...)
})

onUnmounted(() => {
  // 등록한 것을 같은 손으로 되돌린다
  window.removeEventListener('resize', onResize)
  clearInterval(timer)
  viewer.destroy()
})

컴포넌트가 사라지는 순간 모든 자원이 깔끔하게 반환된다. 몇 번을 드나들어도 누수가 없다.

02 / HOOKS

생명주기 훅 지도

Vue 의 생명주기는 몇 가지 핵심 훅으로 표현됩니다. 언제 실행되는지만 알면 충분합니다.

onMounted()

컴포넌트의 DOM 이 처음 화면에 붙은 직후 실행. 외부 라이브러리 초기화, 지도 생성, API 첫 호출에 적합.

언제: 탄생 직후 — 자원을 잡는 타이밍

onBeforeUnmount()

DOM 이 제거되기 직전, 컴포넌트 인스턴스는 아직 살아 있는 상태. 정리 전 마지막으로 상태를 읽어야 할 때.

언제: 사라지기 직전 — 마지막 스냅샷

onUnmounted()

DOM 이 완전히 제거된 후 실행. 이벤트 리스너 해제, watch stop, viewer.destroy() 등 정리의 주 무대.

언제: 사망 직후 — 자원을 돌려주는 타이밍

onScopeDispose()

컴포저블 내부에서 사용. 컴포넌트가 아닌 reactive scope 가 소멸할 때 실행. 컴포저블이 직접 정리를 책임질 수 있다.

언제: 컴포저블 스코프 종료 — 캡슐화된 정리

onMounted ↔ onUnmounted 는 한 쌍이다. onMounted 에서 만든 것은 onUnmounted 에서 되돌린다. 컴포저블 안에서는 onScopeDispose 로 같은 원칙을 지킨다 — 사용하는 쪽이 신경 쓰지 않아도 컴포저블 자체가 정리를 보장한다.

03 / THE DUTY

정리는 의무다

누수의 3대 원천 — 이벤트 리스너, watch 핸들, 무거운 객체. 각각의 정리 짝을 익혀두세요.

정리를 빠뜨리기 쉬운 패턴 세 가지와 올바른 짝을 코드로 살펴봅니다.

① 이벤트 리스너

onMounted(() => {
  window.addEventListener('keydown', handleKey)
})

onUnmounted(() => {
  // 같은 함수 참조로 제거해야 한다
  window.removeEventListener('keydown', handleKey)
})

addEventListener 와 removeEventListener 는 항상 짝이다. 익명 함수를 넘기면 나중에 제거할 수 없으니 반드시 함수 참조를 변수에 저장한다.

② watch / watchEffect stop handle

const stopWatch = watch(
  () => store.routeInfos.value,
  () => renderRouteInfoMarkers(),
  { deep: true }
)

onUnmounted(() => {
  // watch 가 반환한 stop 함수를 호출
  stopWatch()
})

watch() 는 감시를 중단하는 함수를 반환한다. onUnmounted 에서 호출하지 않으면 컴포넌트가 사라진 뒤에도 watch 가 살아서 콜백을 계속 실행한다.

③ 무거운 객체 — Cesium viewer, HTML 오버레이 div

onMounted(async () => {
  await init()             // Cesium viewer 초기화
  setViewer(window.viewer) // viewer 소유권 등록

  // 경로 폴리라인 렌더
  shareViewer.renderSections(sharedData.value.sections)
})

onUnmounted(() => {
  shareViewer.clear()  // 폴리라인 엔티티 제거
  setViewer(null)      // viewer 참조 해제
})

Cesium viewer 는 GPU 자원을 점유한다. HTML 오버레이 div 도 DOM 에 남는다. viewer.destroy() 또는 clear() 를 명시적으로 호출하지 않으면 메모리가 회수되지 않는다.

04 / IN RUNNABLE

init / destroy 패턴

Runnable 의 sideeffect 컴포저블은 init() 과 destroy() 를 한 쌍으로 관리합니다.

지도 페이지가 올라올 때 useMapFeatureInit 이 모든 레이어 sideeffect 를 초기화하고, 스코프가 닫힐 때 onScopeDispose 가 정리를 보장합니다. 카메라 sideeffect 를 예로 보겠습니다. 

// app/widgets/map-page/model/useMapFeatureInit.ts
import { onScopeDispose } from 'vue'

export function useMapFeatureInit({ drawing, routeDrawStore, ... }) {
  const cameraEffect = useCameraSideeffect({ ...camera })

  // 스코프가 소멸하면 camera.moveEnd 리스너를 정리
  onScopeDispose(() => cameraEffect.destroy())

  onMounted(async () => {
    await init()                  // Cesium viewer 초기화
    useMapViewer().setViewer(window.viewer)

    await Promise.all([
      cameraEffect.init(),        // 카메라 이벤트 리스너 등록
      boundaryEffect.init(),      // 행정 경계 레이어 로드
      elevationEffect.init(),     // 고도 레이어 로드
      ...additionalInits.map((fn) => fn())
    ])
  })
}

마찬가지로, 구간 분할 모드를 담당하는 useSplitModeSideeffect 는 split 모드 진입 시 생성한 클릭 핸들러·엔티티 그룹을 스코프 종료 시 일괄 정리합니다. 

// app/features/draw-route/api/useSplitModeSideeffect.ts
import { onScopeDispose } from 'vue'

// split 모드 종료 시 포인트·핸들러 일괄 제거
onScopeDispose(exitSplitMode)

패턴은 일관됩니다 — 컴포저블 안에서 자원을 만들면, 같은 컴포저블 안에서 정리도 등록한다. 사용하는 쪽(컴포넌트나 상위 composable)은 init() 만 호출하고 정리는 신경 쓰지 않아도 됩니다. 이것이 02챕터 캡슐화의 연장선입니다 — 컴포저블이 자기 자원의 전 생애를 책임집니다.

05 / MENTAL MODEL

잡았으면 놓아라

한 문장 멘탈 모델

켜질 때 만든 모든 것 — 리스너·watch·viewer·div — 은 꺼질 때 같은 손으로 되돌려야 한다. 정리를 컴포저블 안에 함께 두면(onScopeDispose), 쓰는 쪽은 누수를 신경 쓸 필요가 없다. 자원의 생성과 소멸이 한 파일 안에서 완결되기 때문이다.

QUIZ / 이해도 체크

학습 완료 퀴즈

4문항 전부 맞히면 이 챕터가 학습 완료로 기록됩니다.

  1. onMounted 에서 window.addEventListener('resize', onResize) 를 등록했다. 컴포넌트가 제거될 때 어느 훅에서 무엇을 호출해야 누수가 없는가?

    • a) onBeforeMount 에서 window.addEventListener 를 다시 호출한다
    • b) onUnmounted 에서 window.removeEventListener('resize', onResize) 를 호출한다
    • c) 별도 정리 없이 Vue 가 자동으로 제거해 준다
    • d) onMounted 안에서 즉시 removeEventListener 를 호출한다

  2. watch(source, callback) 가 반환하는 값의 역할로 옳은 것은?

    • a) 감시 중인 현재 값을 조회하는 getter 함수다
    • b) watch 의 콜백을 즉시 한 번 실행하는 함수다
    • c) watch 감시를 중단하는(stop) 함수로, onUnmounted 에서 호출해야 한다
    • d) watch 를 재시작하는 함수다

  3. 컴포저블 내부에서 onUnmounted 대신 onScopeDispose 를 사용하는 이유로 가장 적절한 것은?

    • a) onScopeDispose 가 onUnmounted 보다 더 빨리 실행되기 때문이다
    • b) 컴포저블은 컴포넌트 외부(예: 테스트 스코프)에서 사용될 수도 있어, 컴포넌트 생명주기에만 묶이지 않고 reactive scope 종료 시점에 정리할 수 있기 때문이다
    • c) onScopeDispose 는 비동기 작업만 정리할 수 있기 때문이다
    • d) onUnmounted 는 Composition API 에서 사용할 수 없기 때문이다

  4. Runnable 의 useMapFeatureInit 에서 cameraEffect.destroy() 를 onScopeDispose 에 등록해 둔 이유는?

    • a) cameraEffect.init() 을 호출하지 않기 위해서다
    • b) 지도 페이지 스코프가 닫힐 때 camera.moveEnd 리스너가 자동으로 정리되어, 사용하는 쪽이 destroy() 를 직접 호출하지 않아도 누수가 없도록 캡슐화하기 위해서다
    • c) init() 보다 destroy() 가 먼저 실행되어야 하기 때문이다
    • d) Cesium viewer 는 스코프가 닫혀야만 초기화되기 때문이다
