플러그인 시스템은
현업에서 어떻게 진화하나

모든 플러그인 시스템은 같은 압력 아래 진화합니다 — 더 늦게 묶고(런타임), 더 적게 신뢰하고(권한·샌드박스), 더 멀리 배포한다(원격·마켓플레이스). 빌드타임 정적 등록에서 시작해 격리된 원격 모듈로 이동하는 공통 궤적을 업계 사례로 정리합니다.

01 / GENERATIONS

4세대 진화 궤적

결합 시점이 빌드타임 → 런타임 → 원격으로 늦춰질수록, 격리와 권한 모델의 요구가 함께 커집니다.

GEN 1 빌드타임 정적 등록 컴파일 시 결합

플러그인이 소스에 같이 번들된다. 호스트가 빌드 시점에 배열/레지스트리로 정적 등록하고, 신뢰는 전제. 격리·권한 개념이 거의 없다.

Webpack / Vite / Babel plugin ESLint / Rollup 정적 registry 배열
GEN 2 런타임 동적 로딩 + 확장점 실행 중 결합

호스트가 "확장점(extension point)/기여점(contribution point)"을 선언하고, 플러그인이 매니페스트로 어디에 무엇을 꽂을지 기술한다. 지연 활성화(lazy activation)로 필요할 때만 로드.

VS Code contribution points Obsidian community plugins Eclipse / IntelliJ
GEN 3 샌드박스 격리 + 권한 모델 신뢰 최소화

서드파티 코드를 메인 스레드 밖(iframe·Web Worker·별도 프로세스)에서 실행하고, 능력(capability)을 명시적으로 허가받은 만큼만 노출. 보안과 성능이 동시 동인.

Figma (QuickJS/iframe) Chrome Manifest V3 Shopify remote-ui / UI Extensions
GEN 4 원격·분산 로딩 + 마켓플레이스 독립 배포

플러그인을 별도 저장소·CDN에서 독립 배포·버전 관리하고, 호스트가 런타임에 원격 모듈을 가져와 합친다. 마켓플레이스·서명·semver 계약이 필수가 된다.

Module Federation / 마이크로 프론트엔드 Backstage plugins Sentry / Datadog 앱 마켓
02 / CASE STUDIES

대표 사례가 푼 문제

각 제품이 "어떤 제약 때문에" 그 구조를 택했는지가 진화의 본질입니다.

VS Code

Extension Host 분리

확장은 UI 스레드가 아닌 별도 Extension Host(Node 프로세스, 웹에선 Web Worker)에서 실행. 느린 확장이 에디터를 멈추지 못하게 격리하고, activation event로 지연 로드.

핵심: 프로세스 격리 · contribution points · 지연 활성화
Figma

신뢰 없는 코드 실행

서드파티 플러그인이 디자인 파일을 건드리므로, 메인 스레드 샌드박스(QuickJS 계열)에서 코드를 돌리고 UI는 iframe으로 분리. 노출 API를 엄격히 통제.

핵심: 메인 스레드 샌드박스 · UI iframe 분리
Chrome MV3

권한·원격코드 축소

background page → service worker, 원격 코드 실행 금지, host permissions·declarativeNetRequest로 능력을 좁힘. "필요한 만큼만" 권한 모델의 표준 사례.

핵심: 최소 권한 · 원격 코드 제거 · 선언적 API
Obsidian

로컬 우선 + 커뮤니티

JS 번들을 런타임에 로드하는 비교적 개방적(고신뢰) 모델 + 커뮤니티 마켓. 자유도는 높지만 격리가 약해 신뢰·검수에 의존하는 트레이드오프를 보여줌.

핵심: 개방형 API · 마켓 · 신뢰 기반
Module Federation

독립 배포 합성

여러 팀이 따로 빌드·배포한 번들을 런타임에 동적으로 가져와 한 앱으로 합성(마이크로 프론트엔드). 공유 의존성 협상과 버전 정합이 과제.

핵심: 런타임 원격 모듈 · 의존성 공유
Backstage

플러그인이 곧 제품

개발자 포털을 코어 + 플러그인으로 구성. 확장점/extension 모델로 조직마다 다른 화면을 조립. 프론트엔드 플러그인 계약을 표준화하려는 흐름.

핵심: 플러그인 우선 아키텍처 · 확장 계약
Shopify

worker 안의 UI

checkout/admin UI 확장을 Web Worker에서 실행하고 remote-ui로 메인 스레드에 안전하게 렌더 명령만 전달. 호스트 DOM 접근 없이 UI를 그리는 패턴.

핵심: off-main-thread UI · 메시지 기반 렌더
MCP

AI를 위한 플러그인

Model Context Protocol — LLM/에이전트에 도구·데이터 소스를 연결하는 표준. "플러그인 시스템"의 무게중심이 AI 도구 연동으로 확장되는 최신 흐름.

핵심: 표준 프로토콜 · 도구 연결 계약
03 / EVOLUTION AXES

진화를 만드는 6개 축

제품은 달라도 변화의 방향은 거의 같습니다. 각 축에서 왼쪽 → 오른쪽으로 이동합니다.

결합 시점
빌드타임 번들→런타임 · 원격 로드

정적 import 배열에서, 활성화 시점에 동적으로 불러오는 lazy/remote 로딩으로.

신뢰 모델
전체 신뢰→능력 단위 허가

"다 줄게"에서, 매니페스트로 선언한 권한(capability)만 노출하는 최소 권한으로.

실행 격리
같은 스레드→worker · iframe · 프로세스

호스트와 한 컨텍스트에서, off-main-thread 샌드박스 + 메시지 통신으로.

API 계약
암묵적 내부 접근→버전드 공개 SDK

내부 모듈 직접 참조에서, semver로 관리되는 안정적 공개 표면으로.

확장 지점
하드코딩 분기→선언적 슬롯/기여점

if 분기로 끼우던 것을, 호스트가 정의한 슬롯에 매니페스트로 기여하는 방식으로.

배포·신뢰성
코어와 함께 배포→마켓 · 서명 · 검수

코어에 묶여 배포되던 것이, 독립 배포 + 서명·심사 마켓플레이스로.

04 / FRONTIER

지금 움직이는 최전선

2024–2026 구간에서 두드러지는 흐름입니다.

WASM 플러그인 언어 비종속 + 강한 격리. Extism 같은 런타임으로 Rust·Go·JS 등을 WASM으로 컴파일해, 호스트 함수만 노출하는 안전한 샌드박스에서 실행. JS 외 생태계까지 플러그인 작성자 확대.
하드닝 JS untrusted JS를 안전하게. SES(hardened JavaScript)·QuickJS-in-WASM로 전역 오염 없이 서드파티 스크립트를 격리 실행. Figma·결제 위젯류가 채택하는 방향.
off-main-thread UI 호스트 DOM 접근 없는 렌더. remote-ui 류 패턴으로 플러그인은 Worker에서 "무엇을 그릴지"만 보내고, 실제 DOM은 호스트가 그림. 성능·보안 동시 확보.
AI · 에이전트 플러그인의 새 소비자가 LLM. MCP 등 표준으로 도구·데이터를 에이전트에 연결. "사람이 쓰는 UI 확장"과 "AI가 쓰는 도구 확장"이 같은 계약 위에서 수렴 중.
서버사이드 확장 엣지/서버에서 도는 플러그인. 엣지 함수·서버리스에 사용자 코드를 격리 실행해 백엔드도 확장 가능하게. 프론트 전용에서 풀스택 확장으로.
05 / WHERE RUNNABLE STANDS

Runnable plugins-ext 의 현재와 진화 경로

현재 app/plugins-ext/ 는 Gen 1.5 — 빌드타임 정적 registry(Gen 1)에 런타임 슬롯/앵커 주입(Gen 2 초입)을 얹은 형태입니다. 매니페스트·슬롯 모델은 이미 업계 표준 궤적 위에 있습니다.

✓ 매니페스트 기반 등록 ✓ 슬롯/확장점 (chip·sidepanel·dashboard·popup) ✓ 8방향 앵커 주입 정적 registry.ts (빌드타임) 격리 없음 (슬라이스 직접 import) 권한 모델 없음
  • 매니페스트 + 슬롯 모델 (Gen 2 핵심) 도입 완료
    PluginManifest 로 슬롯·위치·기본 활성 선언, 호스트가 자동 주입. VS Code contribution point 와 같은 발상.
    app/plugins-ext/types.ts · registry.ts · MapOverlays.vue
  • 호스트 API 계약 분리 (축: API 계약)
    플러그인이 features·entities를 직접 import 하는 대신, 안정적인 plugin context/SDK 표면만 받게 하면 결합도↓·교체 안전성↑.
    plugins-ext/* → 공개 컨텍스트 주입형으로
  • 런타임 동적 로딩 (축: 결합 시점)
    정적 registry 배열 → defineAsyncComponent/동적 import 로 필요 시 로드. 활성화 이벤트(lazy)로 초기 번들 절감.
    registry.ts · usePluginSurfaces.ts
  • 권한·격리 검토 (축: 신뢰·격리)
    서드파티/원격 플러그인을 받을 계획이 생기면 capability 선언 + iframe/Worker 격리를 도입. 현재처럼 1st-party만이면 과설계 — YAGNI 기준으로 시점 판단.
    필요 시점에만 — 지금은 결정 보류
