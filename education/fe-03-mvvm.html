Runnable · Frontend Lecture · 03

화면과 상태를 잇는 방법
— MVVM

앞 챕터에서 "데이터가 바뀌면 화면이 알아서 따라온다"는 반응형을 배웠습니다. 그렇다면 그 데이터를 어디에 두고, 어떻게 정리해서, 누가 화면에 넘겨줄까요? 오래된 답은 MVC였지만, 반응형 시대의 답은 MVVM 입니다. 이 챕터는 MVC를 넘어 왜 MVVM인지, 그리고 Runnable의 store가 어떻게 이미 ViewModel인지를 다룹니다.

난이도 ★★☆ 선행: 02 컴포저블 키워드 mvvm
01 / WHAT

MVVM 은 세 칸짜리 구조다

MVVM = Model · View · ViewModel. 식당으로 비유하면 한눈에 들어옵니다.

Model — 창고

가공 안 된 원재료. 서버 응답, DB 행(row), 순수 데이터 그 자체. 화면이 어떻게 생겼는지는 전혀 모른다.

예: 서버가 준 route JSON

ViewModel — 주방

원재료를 손질해서 바로 낼 수 있는 접시로 준비. 화면이 그대로 쓰면 되는 상태와, 그 상태를 바꾸는 함수를 들고 있다.

예: 정리된 routeInfos + 토글 함수

View — 테이블

주방이 차려준 접시를 받아서 보여주기만 한다. 요리하지 않는다. 화면(.vue)은 ViewModel 값을 읽어 그릴 뿐.

예: routeInfos 를 그리는 .vue

핵심은 책임 분리입니다. 데이터를 어디서 가져오는지(Model), 화면이 쓰기 좋게 다듬는지(ViewModel), 어떻게 보여주는지(View)를 한 덩어리로 섞지 않습니다. 테이블 손님(View)이 직접 창고(Model)에 들어가 재료를 꺼내 썰지 않듯이.

02 / VS MVC

MVC 와 MVVM, 결정적 차이는 '바인딩'

두 패턴 다 데이터·로직·화면을 나눕니다. 진짜 차이는 화면을 누가, 어떻게 갱신하느냐입니다.

MVC — Controller 가 View 를 직접 조작

// Controller
model.count++
// 화면을 "내가" 손으로 다시 쓴다
view.label.textContent = model.count
view.refresh()

상태가 바뀔 때마다 Controller 가 직접 View 를 찾아가 갱신해야 한다. 갱신을 빠뜨리면 화면이 데이터와 어긋난다.

MVVM — 바인딩이 View 를 자동 갱신

// ViewModel
count.value++
// 끝. View 는 count 에 "묶여"(bound) 있어
// 값이 바뀌면 알아서 다시 그려진다
<span>{{ count }}</span>

ViewModel 의 상태만 바꾸면, 바인딩이 그 값에 묶인 View 를 자동으로 갱신한다. "어떻게 갱신할지"를 쓸 필요가 없다.

그래서 MVVM 은 01 챕터의 반응형 위에서만 성립합니다. "값이 바뀌면 화면이 알아서 따라온다"는 반응형이 바로 여기서 말하는 바인딩이니까요. 반응형이 토대, MVVM 은 그 위에 세운 집의 구조도입니다.

03 / HISTORY

MVVM 은 어디서 왔나

뿌리는 2005년 Microsoft 의 WPF(데스크톱 UI). 이후 거의 모든 현대 UI 프레임워크가 같은 계열로 수렴했습니다.

WPF (2005)

Microsoft 데스크톱. MVVM 이라는 이름과 양방향 바인딩 개념이 처음 정립된 출발점.

원조 · 데스크톱

SwiftUI

Apple. @State 값이 바뀌면 뷰가 자동으로 다시 그려진다. 같은 바인딩 사상.

iOS · @State

Jetpack Compose

Android. mutableStateOf 로 상태를 만들면 그 상태를 읽는 UI 가 자동 갱신.

Android · mutableStateOf

Vue

웹. ref / reactive 로 만든 상태가 템플릿에 바인딩되어 자동 갱신. Runnable 이 쓰는 길.

Web · ref / reactive

이름과 문법은 제각각이지만 사상은 하나입니다 — "상태를 선언하고, 화면을 그 상태에 묶는다." 그래서 한 플랫폼에서 MVVM 을 익히면 다른 플랫폼으로 건너갈 때 개념이 거의 그대로 옮겨집니다.

04 / VIEWMODEL

ViewModel = 다듬어 둔 상태 + 그걸 바꾸는 함수

정의 한 줄: ViewModel 은 "화면이 바로 쓸 수 있게 다듬어 둔 상태" 와 "그 상태를 바꾸는 함수"의 묶음입니다.

// entities/route/model/useRouteInfoStore.ts — 거의 ViewModel 그 자체
const routeInfos = useState('routeInfo.data', () => [])      // 다듬어 둔 상태
const isLoading  = useState('routeInfo.isLoading', () => false) // 화면용 상태

// 상태를 바꾸는 함수들
const toggleAddingMode  = () => { isAddingMode.value = !isAddingMode.value }
const clearRouteInfos   = () => { routeInfos.value = [] }

return { routeInfos, isLoading, toggleAddingMode, clearRouteInfos }

여기서 View(.vue)는 철저히 dumb 합니다. routeInfos 를 읽어 목록을 그리고, 버튼을 누르면 toggleAddingMode() 를 호출할 뿐 — 직접 데이터를 자르거나 서버를 부르지 않습니다. "무엇을 어떻게 보여줄지를 다듬는 일"은 전부 ViewModel(store) 안에 있습니다. 

// RouteInfoPanel.vue — dumb View
const { routeInfos, toggleAddingMode } = useRouteInfoStore()

<button @click="toggleAddingMode">추가</button>
<li v-for="r in routeInfos">{{ r.name }}</li>
05 / MENTAL MODEL

한 문장으로 기억하라

한 문장 멘탈 모델

MVVM 이란 주방(ViewModel)이 손질해 차려둔 상태를, 테이블(View)이 받아 보여주기만 하는 구조이고, 그 둘을 잇는 끈이 바인딩이다. 주방의 접시가 바뀌면 테이블의 화면이 알아서 바뀐다 — 그래서 View 는 절대 직접 요리하지 않는다.

06 / DEEPER

Runnable store ↔ ViewModel 매핑

MVVM 의 세 계층이 Runnable 실제 파일에 어떻게 1:1 로 내려앉는지 확인합니다.

Model — 서버 응답 원형

서버가 내려주는 가공 전 데이터. shared/types/route.ts 의 타입 정의와 server/services/route.service.ts 의 DB 조회 결과가 여기에 해당합니다. 화면이 어떻게 생겼는지는 모릅니다.

파일: server/services · shared/types

ViewModel — useRouteInfoStore

app/entities/route/model/useRouteInfoStore.ts. 서버 응답을 담아 화면이 바로 쓸 상태 (routeInfos · isLoading · isAddingRouteInfo)와 동기적 뮤테이션 함수 (toggleAddingMode · addDraftRouteInfo · clearRouteInfos)를 한 상자에 묶습니다.

파일: entities/route/model/useRouteInfoStore.ts

View — *.vue 컴포넌트

RouteInfoPanel.vue 등. ViewModel 에서 const { routeInfos, toggleAddingMode } = useRouteInfoStore() 를 한 줄로 꺼내 쓰고, 바인딩(v-for · @click)으로 화면을 그립니다. 직접 서버를 부르거나 데이터를 가공하지 않습니다.

파일: widgets / pages / *.vue

패턴이 성립하는 이유는 useRouteInfoStore 가 Cesium·$fetch 를 전혀 모른다는 것입니다. "지금 routeInfos 가 무엇인지"만 알고, "그걸로 무엇을 할지"는 다음 챕터의 sideeffect 가 담당합니다. 이 경계가 바로 MVVM 의 View 가 "요리하지 않는다"는 약속과 이어집니다.
